1.0.16 - 2026-10-01
-------------------
- 新增：配方不使用电路时，自动把目标容器的电路置空。起因是“配方本身没有电路要求，但它的材料在有电路时走的是另一个配方”，发送后机器跑的是另一个配方。根因是格雷科技按“搜索键”匹配配方：不使用电路的配方不会产生任何电路键，机器里留着的电路编号不会妨碍它被选中——于是“不需要电路的配方”和“要求该编号的配方”会同时成为候选，谁先被搜到就跑谁。现在发送这类配方时，只要目标容器有电路槽，就把电路清空（直接清空电路槽：空槽与写入电路 0 对本整合包的配方匹配完全等价——不存在显式要求电路 0 的配方；之所以不写 0 而是真清空，是因为 GT 的电路 0 也是一块带 NBT 的真实编程电路物品，留在槽里容易被当成没生效），提示框多显示一行“电路置空”。
- 不做机型判断：机器支持哪些配方由格雷科技自己决定，模组不替它把关——只要是识别出的格雷配方、且不使用电路，目标容器有电路槽就置空。置空走独立数据包 ClearContainerCircuitPacket（只带容器菜单编号，与写编号的包分开），目标没有电路槽时服务端取不到机器实例，直接什么都不做。提示行按同一件事判断：目标没有电路槽（原版箱子、漏斗等）时连“电路 #N”都不再显示。以下情况一律不动电路：不是格雷配方或识别失败、目标不是格雷机器界面、没有电路槽、电路槽里放的不是编程电路、处于反转取回模式。
- 说明：既有的“按配方写入电路编号”行为没有变化，改动只发生在配方不使用电路的场合。网络协议版本由 3 升到 4（新增一个数据包，客户端与服务端需同时更新）。

1.0.13 - 2026-09-29
-------------------
- 新增：反转搜索共用 FindMeExtended 的容器黑名单。黑名单本体做在 FindMeExtended 1.0.2 里（黑名单工具、持续高亮、潜行右键加入 / 潜行左键移出、按维度存档、只认坐标，见该模组的说明），本模组不再自己维护一份，只在反转搜索里把黑名单坐标排除掉：被列入黑名单的容器既不计入“背包与周围现有 X 份”，也不会被取回，与 FindMeExtended 自己的“查找物品 / 取出物品”口径一致。
- 适配方式：新增 FindMeExtendedAdapter.blacklistedPositions(ServerLevel)，通过反射读取对方的公开接口 com.lai.findmeextended.api.FindMeBlacklistApi#blacklistedPositions（返回该维度黑名单坐标的只读视图）。接口单独解析、允许缺失：FindMeExtended 未安装、或版本旧到没有这个接口时只退化成“不排除任何容器”，反转搜索本身照常工作——与现有的可选依赖处理方式一致，不会像 1.0.5 那样一处失败就整体关闭。
- 过滤位置与 FindMeExtended 本体一致：在 FindMeExtendedAdapter 收集方块实体那一步排除，snapshotNearby（统计）与 pullAll（取回）共用同一份过滤器，被排除的容器连一次方块状态查询和提取器调用都不会发生。每次统计或取回只解析一次接口、只构造一次过滤器；黑名单为空时用常量过滤器，连哈希查表都省掉。
- 说明：双箱子的两半共用同一份库存，而黑名单只记坐标较小的那一半（FindMeExtended 在增删时归一化）。本模组这边本来就只扫描坐标较小的那一半（见 1.0.1 的重复计数修复），因此归一化坐标一定命中，点哪一半加入黑名单都一样有效。
- 说明：本模组不再包含任何黑名单实现。开发过程中的中间版本曾把黑名单（含工具、高亮、网络包）做在本模组里，现已整体移入 FindMeExtended，本模组只保留只读适配；网络协议保持版本 3，未新增数据包。
- 说明：AE2 的“整个网络的聚合视图”无法按单个容器排除。存储总线把某个容器挂进网络后，物品是通过网络视图读到的，把这个存储方块列入黑名单不会让它的物品从网络视图里消失。
- 依赖：反转搜索的黑名单需要 FindMeExtended 1.0.2 或更高版本；mods.toml 的可选依赖范围仍保持 [1.0.1,)，旧版本只会少掉黑名单这一项。

1.0.12 - 2026-09-22
-------------------
- 修复（关键）：反转 Z 取回时，通配符输入（格雷的电路标签，例如 HV 传感器配方里的 HV 电路）会锁死在存量最少的那一份上；那一份取不回来就整项失败，旁边同一标签下存量几百的另一份却从头到尾没被碰过。
  现场核实：玩家在 HV 传感器配方上反复按反转 Z，每次都只报「取回 微型处理器集群 时仍短缺 2」（12 次）。读存档确认，附近只有一台 gtceu:mv_circuit_assembler 的输入槽里有 2 个 micro_processor_assembly；而同在搜索范围内、同样满足 #gtceu:circuits/hv 的 gtocore:item_vault 里有 284 个 advanced_integrated_circuit。实测三种布局也印证了这一点：外部容器放 0 个（AE 里有 200 多个）取回 0 个；放 1 个取回 1 个；放 2 个取回 2 个——取回数量恰好等于外部容器里的存量。
- 根因：createPlan 对每一项材料是「按快照顺序取第一个匹配的容器」，而快照顺序是背包 → 各容器自己的 Forge 物品处理器（按区块遍历顺序）→ AE2 视图（排在最后）。电路装配机落在最后一个区块，保险库的内容由 AE2 网络视图提供、排在末尾，于是只有 2 个的 micro_processor_assembly 先被选中。配方明明是通配符（任意 HV 电路都合法），规划却只认这一种；pullAll 又只照这一个具体物品去取，取不到就直接判定短缺，从不回头用同一标签下的其他成员。1.0.11 及之前一直如此，只是以前电路恰好放在普通容器里、取回成功，所以没暴露。
- 改法（三处，都不改网络协议——服务端本来就收到了每个配方项的 wildcard 标志和完整候选列表）：
  1) 规划时把匹配到的容器按存量从多到少排序再消耗。存量多的那份更可能取回成功，也避免为了凑数去啃只剩一两个的容器。
  2) 取回时按候选顺位尝试：先取存量最多的那个，取不够就换同一配方输入下的下一个候选，最多换 4 个（电路标签一般三到六个成员，且每换一次都要重扫一遍搜索范围，不能再大）。候选只有一个时这个上限自然退化成原来的「重试一次」，行为不变。
  3) 新增一条自己的 AE2 取回通路，不再只靠 FindMeExtended 的 AE2 提取器。它那套做法是「拿 ItemStack 反推 AE 物品键，再用 isSameItemSameTags 逐字节比 NBT」——而我们的需求本来就是 AE 物品键的产物（快照里是 AEItemKey.toStack），反推回去再比一次 NBT 是多余的一步，中间任何一处 NBT 表示差异都会静默地取不回来。现在改成直接遍历存储给出的可用物品键，并用**存储自己给出的那个键实例**去 extract：已核对 GTO 源码，MultiblockMEStorageMachine.extract 走的是 keyMap.extract，而 AEKeyMap 是 Reference2LongOpenHashMap（引用同一性），换个实例去取必然返回 0。匹配优先「物品 + NBT 完全相同」，整个存储里都没有时才退回「同一种物品」——配方只认物品本身（通配符输入尤其如此），为了 AE 侧键带不带 NBT 的差异把材料判成取不回来并不合理。
- 说明：这三条里第 3 条是补充通路，独立解析、允许失败。AE2 版本不合导致它解析不了时只关掉它自己，FindMeExtended 的提取器、快照和去重照常工作，不会像 1.0.5 那样一处失败就整体关闭。
- 说明：同一物品的多项需求仍然合并成一次取回请求（配方把同一种材料拆成两格很常见，格雷的传感器配方就是两个 HV 电路格），所以正常情况下扫描次数与 1.0.11 相同，只在真的取不回来时才会多扫几次。
- 说明：这一版把「通配符」的语义在取回侧补齐了。之前只有「够不够」的统计认通配符（RecipeIngredientSpec.matches 的 wildcard 分支），「取回来」这一侧只认单个具体物品，两侧语义不一致正是这个 bug 的来源。
- 待实测：AE 侧取回是否修好，需要你在游戏里复现一次原来的场景确认（外面容器清空、只留 AE 里那批 HV 电路，对 HV 传感器配方按反转 Z）。

1.0.11 - 2026-09-22
-------------------
- 修复（关键）：1.0.10 没修好的那个重复计数。物品保险库接进 AE 网络后，材料被算成两份，真正的原因不在保险库自己，而在**范围内的 AE 接口**。
  已核对字节码：appeng.helpers.InterfaceLogic.getCapability 把 Capabilities.STORAGE 映射到 getInventory()，而 getInventory() 是 hasConfig ? getLocalInventory() : networkStorage——接口**没有配置**任何物品时，它暴露出去的就是 networkStorage。networkStorage 在 gridChanged() 里被赋值为 getGrid().getStorageService().getInventory()，StorageService 里那是个 private final NetworkStorage storage 字段，也就是 appeng.me.storage.NetworkStorage，**整个 ME 网络的聚合存储**。
  于是存储总线把保险库挂进网络后，同一份保险库有了两个来源：保险库方块自己的 MEStorage（MultiblockMEStorageMachine 实现 MEStorage，getCapability 在 side 为 null 或正面时返回自己），以及接口暴露的网络聚合视图（里面含保险库）。两个都被读走，材料就是两份。这解释了为什么只摆保险库（没有网络、范围内没有接口）时一切正常。
- 改法：读 AE2 存储时把视图分成两类，物理视图（方块自己的库存）与网络视图（NetworkStorage，即整个网络的聚合），最后按**内容包含**去重——某个物理存储的每种物品在网络视图里都有至少同样多，就说明这份库存已经在网络里了，不再单独计入；网络里没有的（该容器没接进这个网络）照旧单独计入，不会漏。
  之所以按内容而不是按「谁属于谁」判断：存储总线挂进网络的是它自己的一层包装 StorageBusPart$StorageBusInventory，拿不到被包装的那个方块，对象身份对不上；而「每种物品都不少于」是很强的条件，只有真的同一份库存才会满足。
  性能：不增加任何一次读取。视图先按物品键收成快照（原始键的 equals/hashCode 稳定），去重只是哈希查表，被去重掉的那份连 ItemStack 都不用转；分类只多一次 isInstance。
- 说明：NetworkStorage 这个类名单独解析、允许缺失，AE2 若改掉它只是退化成没有这层去重，不会连带关掉整个 AE2 支持。
- 说明：1.0.10 里「暴露了 AE2 存储就不再读该方块的 Forge 物品处理器」这条保持不变——它对保险库是对的（GTO 的 AEItemKeyStackHandler 只返回 keyMap 第一个物品键，且数量是全量，读它既重复又不准），只是它单独并不能解决重复计数。

1.0.10 - 2026-09-22
-------------------
- 修复（**根因判断有误，实际无效，见 1.0.11**）：GTO 的物品保险库（多方块）旁边的材料会被算成两份。当时认为原因是保险库把同一份库存同时挂成两个接口——Forge 的物品处理器和 AE2 的 MEStorage（控制器是 MultiblockMEStorageMachine，仓是 MEStorageHatch，两者指向同一份 keyMap），两条路都读于是同一批物品被计了两遍。
  改法：同一个方块实体只要暴露了 AE2 存储，就不再读它的 Forge 物品处理器。这既省掉一次读取（性能上只减不增），也顺带解决多个保险库仓重复计入的问题——各仓与控制器共用同一个 MEStorage 对象，本来就被身份去重吃掉，跳过处理器后不会再各加一份。
  说明：保险库的 Forge 物品处理器本身也是残缺的（GTO 的 AEItemKeyStackHandler.getStackInSlot 只返回 keyMap 里的第一个物品键，且数量是全量），读它既重复又不准，AE2 视图才是完整的那份，所以是「有 AE2 存储就跳过处理器」，不是反过来。这一条结论本身没错，保留到 1.0.11；错的是以为它能单独解决问题。
  ME 箱 / ME 驱动器不受影响：它们走的是按存储元件逐个读取的分支，元件与机器自己的内部槽位不是同一份库存，物品处理器仍然照读。

1.0.8 - 2026-09-20
------------------
- 修复（关键）：在 EMI 配方树（合成树）里按住 Z 完全没有反应。根因是 EMI 的悬停查询在配方树上必然查不到东西：配方树界面不是容器界面，EMI 也没有为它注册 EmiStackProvider，而合成树节点画 tooltip 走的是 List<ClientTooltipComponent> 重载，lastStackTooltipRendered 的兜底只挂在 GuiGraphics.drawItemTooltip(Font, ItemStack, int, int) 上——三条路全部落空，EmiApi.getHoveredStack 在树上返回 EMPTY。现在直接向配方树界面索取它自己的悬停节点（BoMScreen.getHoveredStack），反射读取节点的原料与配方。目标容器仍由 EmiApi.getHandledScreen() 给出，它在配方树下会退回界面背后那个容器界面，因此“在合成树上挑一个配方、把材料发到背后打开的机器”可以正常工作。
  说明：这一步用了反射，因为配方树的悬停方法返回的是它的 private 内部类，编译期拿不到。按结构识别而不绑死内部类名——内部类直接从方法返回值类型取，节点类再从 node 字段的类型取，EMI 重命名内部类不会让这里失效；任一环节失败只关掉配方树识别，侧栏与容器槽位等其余入口照常工作。
- 修复：选择份数时莫名中断的最后一处来源。判定“鼠标是否还在目标配方上”由引用相等改为结构比较（配方比 ID + 类别，原料比 EmiIngredient.areEqual）。EMI 会在玩家背包变化时重建侧栏条目（EmiFavorites.updateSynthetic 先清空再重建 syntheticFavorites，而 FAVORITES 侧栏是直接指向那份列表的实时视图），配方树重算时也会重建节点；同一个物品配同一个配方、对象却被换掉，引用相等会把这种“换了对象但目标没变”误判成鼠标离开。合成树里“改用另一种材料”那种节点（EmiResolutionRecipe）的 ID 是 null，这类仍只能靠引用判断，比较保守但不会误判。
- 修复：选择期间滚轮事件在配方树下也会漏给 EMI。BoMScreen.mouseScrolled 会把滚轮当成缩放，在份数框上还会改 BoM.tree.batches 并重算整棵树。现在选择期间滚轮无条件吞掉（含等待服务端统计结果的那几 tick，攒下的格数在结果回来时补上）。
- 修复：本模组记录的鼠标位置不再取自 EMI。EmiScreenManager 只在容器界面与它自己的配方界面里更新鼠标记录，打开配方树后不再刷新，拿到的会是进入配方树之前的位置；改为在渲染事件里自己记录（该事件对每个界面都会触发）。
- 说明：合成树本身不会周期性重算。recalculateTree() 只在界面初始化、鼠标点击、Ctrl+R/C、以及在份数框上滚动时调用，与背包或 AE 面板的实时统计无关，因此“树上实时刷新导致选择中断”这个猜测不成立——真正的原因就是上面第一条：在树上根本识别不到目标。

1.0.6 - 2026-09-17
------------------
- 修复（关键）：日志出现“未找到可用的格雷科技电路接口，电路自动配置功能已关闭”，导致读电路和写电路一起失效，按住 Z 既不显示“电路 #N”、发送后电路也不变。根因是 1.0.5 的反射入口解析把一堆查找塞进了同一个 try 块，采用“全有或全无”的判断——任何一项失败（某个类在对方版本里挪了包、某个方法改了签名）都会把整个功能一起关掉，连根本不需要那个类的“读电路”也被牵连。现在每一项单独解析、单独记录失败原因，任何一项失败只关掉它自己对应的能力。
- 修复（关键）：整个兼容层不再绑死类名，改成按结构识别，避免再被版本差异一枪打死：
  1) 读电路：优先用 IntCircuitBehaviour；该类不存在时退回“注册名 *:programmed_circuit + NBT 键 Configuration”，完全不依赖格雷科技的任何类。只要整合包里存在编程电路物品，读电路就能用。
  2) 写电路：不再检查机器是否实现 IHasCircuitSlot，改成鸭子类型——只要机器（或其父类）有无参方法 getCircuitInventory() 且返回可写物品槽，就往第 0 格写；isCircuitSlotEnabled() 存在时用它把关（蒸汽总线靠它关掉电路槽），不存在则视为可用。
  3) 找机器：不再检查菜单是不是 ModularUIContainer，改成先找无参方法 getModularUI()，找不到再找类型名含 ModularUI 的字段；拿到 ModularUI 后读 holder 字段，找不到就找类型名含 IUIHolder 的字段。这样 LDLib 改包名或改字段名都不会失效。
  4) IntCircuitBehaviour 的方法查找先按精确签名找，找不到再按“名字 + 参数个数”放宽。
- 新增：每一步诊断直接打到聊天栏（前缀 [电路]），不用退出游戏翻日志。按住 Z 时会依次说明：配方 ID 与配方类、格雷接口哪些入口不可用、通路1（EMI 原料列表）扫到了几项催化剂/输入、通路2（直接翻配方内部数据）找到了什么配方对象和哪个字段、最终结论是几号电路；松开 Z 时会说明已向服务端提交的容器号与电路号；服务端会回报真实结果——写入了哪台机器、目标没有电路槽、目标不是格雷界面、还是写入失败。同一个配方只详细输出一次，最多 40 个配方。

1.0.5 - 2026-09-17
------------------
- 修复：1.0.4 的电路识别在格雷科技整合包（GTO）里完全失效，表现为按住 Z 不显示“电路 #N”、发送后电路也不变。根因有两条，都已修正：
  1) 只扫了 EMI 配方的催化剂列表，而 GTO 的 GTEMIRecipe 把 getFlatWidgetCollection 覆写成返回空列表，ModularEmiRecipe 构造器不再从界面槽位收集原料；它改在 getInputs() 里懒初始化，并顺带把零概率输入补进催化剂列表。原来先读催化剂再读输入，读到的是空列表。现在先调 getInputs() 触发初始化，再重新读催化剂。

- 新增：电路识别失败时打印诊断日志（每个 GT 配方一次，最多 64 条）：配方 ID、配方类名、催化剂/输入项数、检测结果，未识别出电路时还会列出前若干项原料的物品 ID 与 NBT，便于定位是配方确实不需要电路还是识别漏了。
